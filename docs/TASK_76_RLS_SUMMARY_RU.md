# Задача [76] - RLS на критичных таблицах - Краткое резюме

## Что сделано

Создана полная миграция Row Level Security (RLS) для защиты критичных таблиц базы данных от прямого доступа через Supabase JS SDK.

## Проблема

Без RS любой пользователь с публичным Supabase anon ключом может:
- Просматривать все бронирования всех пользователей
- Изменять или удалять чужие бронирования
- Получать доступ ко всем профилям пользователей
- Добавлять/удалять избранное за других пользователей

RLS гарантирует, что **каждый запрос** фильтруется на уровне базы данных на основе идентификатора и роли авторизованного пользователя.

### Ключевые функции безопасности

#### 1. Проверка ролей из базы данных
Все проверки администратора используют функцию `is_admin()`:
```sql
CREATE OR REPLACE FUNCTION public.is_admin()
RETURNS BOOLEAN
LANGUAGE plpgsql
SECURITY DEFINER  -- Обходит RLS
SET search_path = public  -- Защита от инъекций
STABLE
AS $$
BEGIN
  RETURN EXISTS (
    SELECT 1 FROM profiles
    WHERE id = auth.uid() AND role = 'admin'
  );
END;
$$;
```

**Почему это важно:**
- Клиентский `user_metadata` можно подделать
- Роли в базе данных - единственный источник истины
- SECURITY DEFINER предотвращает бесконечную рекурсию

#### 2. Предотвращение рекурсии RLS
Все политики используют `(SELECT auth.uid())` вместо `auth.uid()` для избежания проблем рекурсии PostgreSQL RLS.

#### 3. Принцип наименьших привилегий

Каждая таблица следует минимальным моделям доступа:

| Таблица | Кто читает | Кто пишет | Кто удаляет |
|---------|-----------|-----------|-------------|
| profiles | Свой + Админ | Свой + Админ | Только админ |
| bookings | Владелец/Хост/Админ | Владельцы создают, Хосты/Админ обновляют | Только админ |
| favorites | Только свой | Только свой | Свой + Очистка хостом |
| reviews | Публично (чтение) | Свой | Владелец/Хост/Админ |
| property_availability | Публично (чтение) | Хост/Админ | Хост/Админ |
| property_ical_feeds | Хост/Админ | Хост/Админ | Хост/Админ |
| notifications | Свой + Админ | Любой авторизованный | Н/Д |
| audit_logs | Только админ | Любой авторизованный | Н/Д (только добавление) |

## Найденные и исправленные проблемы

### Проблема 1: Каскадное удаление при удалении property
**Проблема:** `deleteProperty()` пытается удалить связанные записи в `reviews`, `property_availability`, `property_ical_feeds`, и `favorites`. Без правильных политик это не сработает.

**Решение:** Добавлены политики, позволяющие хостам property удалять связанные записи:
```sql
CREATE POLICY "reviews_delete" ON reviews
  FOR DELETE
  USING (
    (SELECT auth.uid()) = user_id
    OR (SELECT is_admin())
    OR EXISTS (
      SELECT 1 FROM properties
      WHERE id = reviews.property_id
      AND host_id = (SELECT auth.uid())
    )
  );
```

### Проблема 2: Создание уведомлений для других пользователей
**Проблема:** Сервис уведомлений создает уведомления для произвольных `user_id` (например, уведомление хоста). Это требует более разрешительной политики INSERT.

**Решение:** Разрешено любому авторизованному пользователю создавать уведомления:
```sql
CREATE POLICY "notifications_insert" ON notifications
  FOR INSERT
  WITH CHECK ((SELECT auth.role()) = 'authenticated');
```

Это нормально - система создает уведомления от имени пользователей, а SELECT/UPDATE все еще ограничены.

### Проблема 3: Очистка избранного хостами
**Проблема:** При удалении property нужно очистить избранное для ВСЕХ пользователей, которые добавили его в избранное, а не только избранное хоста.

**Решение:** Добавлена специальная политика для удаления избранного на основе хоста:
```sql
CREATE POLICY "favorites_delete_by_host" ON favorites
  FOR DELETE
  USING (
    (SELECT auth.uid()) = user_id
    OR (item_type = 'property' AND EXISTS (
      SELECT 1 FROM properties
      WHERE id = favorites.item_id
      AND host_id = (SELECT auth.uid())
    ))
    OR (SELECT is_admin())
  );
```

## Влияние на производительность

**Ожидаемые накладные расходы:** < 5ms на запрос

**Почему минимально:**
- Все колонки политик проиндексированы (host_id, user_id, provider_id, property_id)
- Политики используют EXISTS с индексированными соединениями
- Функция `is_admin()` - STABLE (кешируется в транзакции)
- PostgreSQL эффективно оптимизирует проверки RLS

## План отката

При возникновении критических проблем:

```sql
-- ВРЕМЕННО: Отключить RLS на конкретной таблице
ALTER TABLE bookings DISABLE ROW LEVEL SECURITY;

# Для повторного включения позже
ALTER TABLE bookings ENABLE ROW LEVEL SECURITY;
# Затем повторно запустите миграцию
```

**⚠️ Внимание:** Никогда не отключайте RLS в продакшене на длительное время.
