# ADR-0001: Модерация — это роль на контроллере, а не доменный сервис

## Статус

Accepted (2026-08-22)

## Контекст

Аудит 3.5 зафиксировал архитектурную неоднородность: `bookings/properties/services`
следуют clean layering, а `directory` (872 LOC) и `forum` (747 LOC) — плоские
service+repository с дублированными инвариантами (protected-fields firewall ×3,
tier photo limits ×3, author-or-admin guard ×3).

При сплите монолитных сервисов возник выбор: выделять ли отдельные
`*ModerationService` для админских операций (approve/reject listings, resolve reports,
pin/remove posts) или разместить их иначе.

Исходная задача 3.6 уже установила прецедент: авторизация удалена из сервисного
слоя и делегирована декларативным гардам (`RolesGuard` + `@RequireRole`).

## Решение

1. **Сервис повторяет агрегат, контроллер повторяет роль.**
   - `DirectoryListingService` — единственный владелец всей state machine листинга:
     `draft → pending → approved | rejected`. Approve/reject живут здесь же.
   - `ListingClaimService`, `ForumDiscussionService`, `ForumEventService`,
     `ForumReportService` — по одному на агрегат.
   - Админские операции доступны через отдельные контроллеры
     (`directory-admin.controller.ts`, существующий `forum-moderation.controller.ts`)
     под `AuthGuard + RolesGuard + @RequireRole('admin')`.

2. **Инвариант объявляется один раз.** Protected-fields firewall, tier photo limits,
   permission model существуют ровно в одном месте каждый; это доказывается
   инвариантными тестами, написанными против старого кода до рефакторинга.

3. **HTTP-контракт заморожен байт-в-байт.** Роуты, payload'ы, коды ответов не меняются;
   тесты контроллеров проходят без правок и служат критерием приёмки.

4. **Сервисы не содержат авторизации.** Никаких `getUserRole()` в сервисах;
   проверка роли — только гарды через единый `UserRolesRepository`.

## Последствия

+ Каждый инвариант имеет единственного владельца — устранён drift protected-fields
  списков между draft/publish/create.
+ Модель согласована с решением 3.6 (нет двух механизмов авторизации).
− Сервис содержит переходы статусов разных ролей (owner publish vs admin approve);
  читателю нужно смотреть на контроллеры, чтобы понять доступность операций.
− «Модерация» как термин не соответствует ни одному модулю — только роутам и гардам.

## Альтернативы

- **Отдельные `*ModerationService`** — отвергнуто: модерация — роль, а не домен;
  такой сервис фрагментировал бы владение одной state machine между двумя классами.
- **Полный clean layering (entities/VO) для directory/forum** — отвергнуто: анализ
  показал <10% чистой доменной логики; основную массу составляет клей
  (нормализация, кэш, email-glue), который лечится схемой нормализации и хелперами,
  а не слоями.
